# Hardwood StatScout: backend and data pipeline

Loads when a matching file is read; update it here. The metric, category and schema contract is `handoff/NBA_CONTRACT.md`; `backend/README.md` has the run commands.

- **Data source**: hoopR-nba-data (sportsdataverse, an ESPN mirror) parquet on GitHub: player box, team box, shots, play-by-play, schedule, plus `player_core`/`rosters`/`draft` for profiles. No API key, cloud-IP friendly, rebuilt nightly. `backend/hoopr.py` reads it (`HOOPR_CACHE_DIR` caches downloads); `backend/nbacodes.py` (stdlib) holds the season rule, team codes, week numbering and the Supabase project guard.
- **Season rule**: hoopR names a season for the year it ends. `season = year + 1 if month >= 10 else year` (October 2026 is 2027). The app renders the integer as `"2025-26"`. `STATCAST_SEASON` (name kept for workflow compatibility) overrides. Oldest supported season is 2003.
- **Tables**: `player_snapshots` (PK (id, season, season_type); `id` is the ESPN athlete id; `player_type` is `g`/`f`/`c`/`unknown`). `player_game_logs` (PK (player_id, season, season_type, game_date, player_type); `game_id` text, `plays` = possessions used, `touches` = minutes, metrics jsonb of raw counts and team context). `player_recent_form` stores the league-anchored 1/2/4-week windows. Publisher rows carry nullable `refresh_id`, `source_published_at`, `published_at`. Schema is the football schema unchanged: no NBA migration was needed.
- **Categories** (`metrics[].category`, exact strings): `Scoring`, `Shooting`, `Playmaking`, `Rebounding`, `Defense`, `Impact`. Every player is eligible for every category; percentiles are ranked within (season, season_type, player_type, category) among qualified players.
- **Weeks**: the NBA has no league weeks. `week` is calendar weeks from a fixed per-season epoch (Monday on or before October 1 of the first calendar year; 2025-09-29 for season 2026), continuing through the playoffs. `max_week`, `start_week`, `end_week` and the publisher's regression guards all use it.
- **Shot zones** (`backend/shots.py`): the rim is NOT at 41.75 ft in ESPN's frame. It is calibrated per season from the dunk and layup centroid (41.6 in 2004, 40.9 in 2011, 39.8 in 2025) and the build fails if that is more than 3 ft from nominal or off-centre. Misses are classified as threes from the play-by-play row (`points_attempted`, else the text), with a distance fallback. Corner three = three, |y| >= 22, within 9 ft of the rim's depth (the contract's `41.75 - 14` shorthand sweeps sideline wings into the corner).
- **On-Off** (`backend/lineups.py`): the floor is replayed from substitutions and scoring events and validated per player-game against box plus/minus (and the final score against the box). Substitutions inside a free-throw stoppage take effect after the last free throw; subs logged before the foul are "immediate" in recent seasons and "deferred" earlier, chosen per season by whichever matches more box plus/minus. Score columns in the feed are unreliable before 2020, so points come from scoring events, with missing events recovered from the score columns. A phase publishes On-Off only when >= 97% of its player-games validate, and a player only when all of his games do.
- **Data refresh workflows**: `.github/workflows/nightly-statcast.yml` (name kept); manual `gh workflow run nightly-statcast.yml`. Supabase is the dedicated "Basketball" project (creds in `~/.basketball_credentials`; migrations in `supabase/migrations/`). Every writer goes through `nbacodes.basketball_client()`, which refuses the Football project host by name; set the repo variable `BASKETBALL_SUPABASE_HOST` to pin the exact host.
- **Self-scheduled refresh**: GitHub cron is unreliable, so every refresh run ends with `schedule-next`, which dispatches `.github/workflows/refresh-timer.yml` with the planner's `wait_seconds`; the timer sleeps (max 5h45m, newest timer cancels older ones) and dispatches the refresh workflow with `planned=true`. Cron (`7,37` October through June, daily July through September) is only a backup that restarts a broken chain. Manual dispatches without `planned` force a probe.
- **Planner cadence** (`backend/refresh_schedule.py`; stdlib plus pyarrow, installed in that workflow step): reads tip-off times from `public.games` and probes every 30 minutes from tip-off +3h to +8h, hourly to +30h, every 30m/1h/3h while a posted final has no `player_game_logs` rows (up to 5 days), else every 6 hours October through June and daily July through September. It re-syncs `games` from the hoopR schedule parquet every 15 minutes while a game is in progress, else daily. Planner errors fall through to probing. `workflow_dispatch` always forces both.
- **Event-aware probe**: `backend/source_probe.py` HEADs the five assets a build reads (player_box, team_box, shots, pbp, schedule for the season) and fingerprints ETag, Last-Modified (usually absent on raw.githubusercontent.com) and Content-Length. The ETag is a content hash, so an unchanged file never retriggers a build. Player box, team box and schedule are required; shots and pbp are optional but still in the fingerprint. `workflow_dispatch` supports `force=true`. Serialized `nba-data-refresh` concurrency group, `cancel-in-progress: false`.
- **Atomic publication**: `backend/refresh.py` rebuilds the current season in full, stages snapshots, game logs and Recent Form under one `refresh_id`, probes before and after the build, then calls `publish_data_refresh` (`20260912000000_event_aware_refresh.sql`). That RPC validates key uniqueness, coverage, same-season regression and exact existing `game_id` retention before replacing the phases in one transaction. Before staging, `refresh.py` hashes its output (ignoring `updated_at` and publish stamps); if it equals `data_refresh_state.last_success_content_hash` it calls `mark_data_refresh_unchanged` instead. `python backend/refresh.py --dry-run --season 2026 --out DIR` builds the candidate without a database.
- **Freshness endpoint**: the app reads `public.data_refresh_status` (`/rest/v1/data_refresh_status?select=*&limit=1`). `ngs_status` and `pfr_status` keep the football column names; here `ngs_status` is the shots feed and `pfr_status` is the play-by-play feed, each `ready`/`pending`/`degraded`/`not_applicable`. A pending or degraded feed publishes the revision as `degraded`. `source_published_at` is null (hoopR files carry no publication time); `published_at` is the user-facing time. `published_season` (migration `20261008000000`) names the season the live revision covers; between the October 1 rollover and opening night the probe reports `status = source_pending`, `last_error_code = season_pending` and `season = <new season>` while `published_season` stays on the old one.
- **Advanced game pages**: after the publish step, `backend/ingest_game_details.py` rebuilds `public.game_details` (team four factors, ORtg/DRtg, pace, paint/fast-break/bench points, biggest lead, player lines with percentiles against the season's team games and 10+ minute player games). The `win_probability` column carries the score margin series `[elapsed_seconds, home_margin]`; `big_plays` are late close scores plus the biggest lead change.
- **Enrichment**: `backend/ingest_enrichment.py` + `team_ratings.py` write `player_profiles` (hoopR bio, draft; contract, snap and injury columns stay null), `team_ratings` (SRS-adjusted net rating per 100 possessions split into offense and defense, shrunk toward last season early) and `game_projections` (rating diff + 2.5 home court, normal with sigma 12). Runs after the publish step and twice a day in `enrichment.yml`.
- **Recent Form covers the newest two seasons**: the live season and the one before it. `DashboardViewModel.recentFormSeasons` is the single source of truth. Windows are 1, 2 and 4 weeks (about 3-4, 7 and 14 games).
- **`backend/prune_history.py` is a manual tool, not a nightly step.** Nothing in the pipeline writes an old season. `--keep` defaults to 2 to match `recentFormSeasons`. Re-ingest an old season with `ingest_game_logs.py --season N --full` + `rollup_recent_form.py --season N`.
- **Historical bundle**: one binary plist per season, `StatScout/Data/players-historical-<season>.plist` (2003 through the last completed season, plus `-0` for the All Time rollup), regenerated via `source ~/.basketball_credentials && python3 scripts/export_historical.py --historical-only`. `project.yml` picks them up with the glob `players-historical-*.plist`, so there is no list to maintain. One file per season because PropertyListDecoder costs about half a millisecond a row: the old single 34 MB file took ~5 s to decode in a release build and blocked an offline first launch. `TwoTierPlayerCache.loadHistoricalSeason(_:)` decodes one season, `loadHistoricalPlayers()` decodes all of them on every core, and the offline fallback shows only the newest season. Past seasons are the only thing the bundle provides. Ahead of the October rollover, fold the outgoing season in early with `STATCAST_SEASON=<next> python3 scripts/export_historical.py --historical-only`. No current-season snapshot ships in the bundle.
- **All Time** (`backend/rollup_all_time.py`): season `0`, summed component by component from the box feed (never from stored snapshots). Career bars: 8,000 minutes regular season, 500 playoffs. Zone metrics pool only seasons from 2004; career On-Off is not published.
- **Local safety**: `backend/.env` is gitignored but is loaded by `python-dotenv`; a copy inherited from the football repo carries Football credentials. The project guard stops a write, but replace the file with Basketball values.
